# راهنمای دیپلوی روی Railway

## ۱. متغیرهای محیطی (Environment Variables)
توکن‌های واقعی از کد پاک شدن و باید تو تب **Variables** پروژه‌ی Railway ست بشن:

| متغیر | توضیح |
|---|---|
| `API_ID` | از my.telegram.org |
| `API_HASH` | از my.telegram.org |
| `BOT_TOKEN` | توکن ربات مدیریتی از BotFather |
| `GOD_ADMIN_IDS` | آی‌دی عددی ادمین(ها)، با کاما جدا کن: `123,456` |
| `AI_API_KEY` | کلید سرویس AI |
| `AI_API_URL` | آدرس endpoint سرویس AI |
| `AI_MODEL` | اسم مدل |
| `DATA_DIR` | (اختیاری) مسیر Volume برای پایدار موندن دیتابیس، مثلا `/data` |

⚠️ توکن‌های قبلی که تو نسخه‌ی اولیه‌ی فایل هاردکد شده بودن لو رفتن (توی این کد و توی
`manager_bot.session` قدیمی که ست کامل نکردم تو این پکیج). **حتماً از BotFather توکن جدید
بگیر و از my.telegram.org هم API_HASH رو ریجنریت کن**، وگرنه هرکسی که اون فایل‌های قدیمی
رو دیده می‌تونه به‌جای تو وارد اکانتت بشه.

## ۲. نوع سرویس
این یه پردازش پس‌زمینه‌ست (نه وب‌سرور)، پس روی Railway باید به‌صورت **Worker** دیپلوی بشه
نه Web Service. فایل `Procfile` همینو مشخص می‌کنه:
```
worker: python bot.py
```

## ۳. لاگین بدون SSH
چون Railway ترمینال تعاملی (SSH) نداره، لاگین کاربر جدید نباید دستی و با ورود کد
تو ترمینال انجام بشه. خبر خوب اینه که این ربات از قبل دقیقاً همین‌طوری طراحی شده:
ربات مدیریتی (`manager_bot`) یه مکالمه‌ی داخل تلگرام داره — شماره موبایل، کد تایید و
(در صورت نیاز) رمز دو مرحله‌ای رو از طریق پیام به خودِ ربات می‌گیره و با
`export_session_string` سشن رو داخل دیتابیس ذخیره می‌کنه. یعنی لازم نیست به سرور SSH بزنی؛
کافیه با اکانت تلگرامت به منیجر بات پیام بدی و مراحل لاگین رو تو چت طی کنی.

## ۴. پایداری دیتا (Volume)
دیتابیس (`bot_data.db`) شاملِ `session_string` اکانت‌های وصل‌شده‌ست — یعنی معادل رمز ورودشونه.
فایل‌سیستم Railway بین دیپلوی‌ها ری‌ست می‌شه، پس اگه Volume وصل نکنی، با هر دیپلوی جدید
همه‌ی اکانت‌های وصل‌شده باید دوباره لاگین کنن. برای جلوگیری از این:
1. از پنل Railway یه **Volume** به سرویس اضافه کن (مثلا mount روی `/data`)
2. متغیر `DATA_DIR=/data` رو ست کن

## ۵. فایل‌هایی که حذف شدن
این‌ها مخصوص هاست cPanel بودن و روی Railway کاربردی ندارن (حذف شدن از این پکیج):
`passenger_wsgi.py`, `keepalive.py`, `cron.log`, و همچنین دیتابیس/سشن قدیمی که سوخته بودن.

## ۶. استریم فیلم (صدا+تصویر) تو ویس‌چت — اضافه شد

قابلیت پخش با `py-tgcalls` + `yt-dlp` اضافه شده (فایل `call_stream.py`). این قابلیت با
همون اکانت خودت (userbot که لاگین کردی) کار می‌کنه، نه با ربات مدیریتی — چون فقط اکانت‌های
واقعی (نه bot token) می‌تونن به‌عنوان assistant به ویس‌چت گروه join بشن و استریم پخش کنن.

### نصب سیستمی لازم
`ffmpeg` باید رو سرور نصب باشه. فایل `nixpacks.toml` این کارو خودکار برای Railway انجام می‌ده،
پس چیز دیگه‌ای لازم نیست تنظیم کنی — فقط مطمئن شو Railway از Nixpacks استفاده می‌کنه
(پیش‌فرض همینه، مگراینکه Dockerfile جدا داشته باشی).

### دستورات (باید از خودِ اکانت لاگین‌شده، تو گروهی که ویس‌چتش استارت شده بفرستی)
| دستور | کار |
|---|---|
| `پخش <لینک>` | شروع پخش یا اضافه به صف. لینک مستقیم، یوتیوب یا اینستاگرام قبوله |
| `رد شو` / `اسکیپ` | رد کردن آیتم فعلی و رفتن سراغ بعدی تو صف |
| `استاپ` / `توقف پخش` | توقف کامل و خروج از ویس‌چت |
| `الان چی پخشه` | نمایش وضعیت فعلی پخش و تعداد صف |

### محدودیت‌ها و نکات مهم
- **ویس‌چت گروه باید از قبل استارت شده باشه** (دستی توسط یکی از اعضا)؛ ربات فقط بهش join
  می‌شه، خودش نمی‌تونه ویس‌چت رو از صفر بسازه.
- کیفیت و سرعت resolve لینک یوتیوب/اینستاگرام به خود yt-dlp و شرایط اون لحظه‌ی سرویس بستگی
  داره؛ گاهی این سایت‌ها فرمت/API‌شون رو عوض می‌کنن و yt-dlp نیاز به آپدیت داره
  (`pip install -U yt-dlp`).
- دانلود/استریم محتوای دارای کپی‌رایت از یوتیوب یا اینستاگرام ممکنه با قوانین استفاده‌ی
  اون پلتفرم‌ها در تضاد باشه؛ مسئولیت محتوایی که پخش می‌کنی با خودته.
- منابع RAM/CPU سرویس Railway محدوده؛ ترنسکد کردن ویدیوی سنگین می‌تونه منابع رو زیاد
  مصرف کنه، پس پلن سرویس رو متناسب انتخاب کن.
